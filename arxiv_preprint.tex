%% Abstract
\begin{abstract}
If you optimise for weighted F1 on an industrial failure-detection dataset, you will
almost certainly build the wrong model for deployment.
This paper is about that problem.
I design a rolling 10-cycle degraded-state counter --- a single scalar derived from
per-unit-normalised sensor composites of the NASA C-MAPSS FD001 benchmark
(20,631 cycles, 100 engine units, 21 sensor channels) --- and train a logistic
regression on it.
I compare it against a Random Forest trained on all 21 raw sensor channels, evaluated
on a unit-level 80/20 split that eliminates temporal leakage.
The logistic regression achieves \textbf{0.98 recall} on at-risk engine cycles;
the Random Forest achieves \textbf{0.88}.
The Random Forest's weighted F1 is higher (0.9576 vs.\ 0.9247).
In a deployment where a missed failure means unplanned downtime or a safety incident,
and a false alarm means an unnecessary inspection, optimising for weighted F1 is the
wrong objective.
The 10-point recall gap is the number that matters operationally.
Full code and the C-MAPSS training file are on GitHub under the MIT licence;
running the Phase~3B notebook cells reproduces every number in this paper.
\end{abstract}

\noindent\textbf{Keywords:} predictive maintenance, feature engineering, C-MAPSS,
logistic regression, random forest, at-risk recall, class imbalance, industrial IoT.

\section{Introduction}
\label{sec:intro}

I started thinking about this problem while working through a forensic data analytics
exercise on industrial sensor telemetry.
The task was straightforward: given run-to-failure machine logs, identify which
units were approaching failure.
I trained a Random Forest on the raw sensor channels, checked the weighted F1, and
it looked fine---above 0.95.
Then I looked at the confusion matrix and noticed how many failing machines the model
was quietly calling healthy.
The overall score was high because the dataset was heavily imbalanced: healthy cycles
outnumbered at-risk cycles by about 5.6 to 1, and the model had learnt to hedge.

That observation is not new.
Class imbalance in predictive maintenance (PdM) datasets is well-documented
\cite{jardine2006review}, and the mismatch between weighted classification metrics
and deployment cost structures has been noted in reliability engineering for decades
\cite{mobley2002maintenance}.
What I found less explored is the specific comparison: does a single temporal feature
derived from domain knowledge of degradation dynamics actually outperform a
high-dimensional sensor ensemble when you evaluate on the metric that matters for
deployment---recall on the at-risk class?

Most C-MAPSS literature focuses on Remaining Useful Life (RUL) regression, where
the goal is to predict a scalar survival estimate \cite{li2018remaining,wu2021temporal}.
That is a different problem.
Binary at-risk classification---is this engine going to fail within the next $N$
cycles?---is closer to what a maintenance system needs to answer in real time.
And for that task, a missed positive (predicting healthy when failure is imminent)
is categorically more costly than a false positive (triggering an unnecessary
inspection).

This paper runs that comparison directly on the NASA C-MAPSS FD001 benchmark.
One model: logistic regression on a single rolling degraded-state counter.
One baseline: Random Forest on all 21 raw sensor channels.
Both evaluated on a unit-level 80/20 split---no temporal leakage.
Primary metric: recall on the at-risk class.
The logistic regression wins by 10 points (0.98 vs.\ 0.88).
The Random Forest's weighted F1 is higher.
The paper argues that is the less important number.

\section{Related Work}
\label{sec:related}

The C-MAPSS benchmark \cite{saxena2008damage} has attracted a large body of work, most
of it aimed at RUL regression.
Li et al.\ \cite{li2018remaining} achieve strong RMSE on FD001 with deep convolutional
networks; Wu et al.\ \cite{wu2021temporal} extend this with attention mechanisms across
sensor channels.
These are impressive results, but they address a different question---predicting how
many cycles remain---rather than the binary question of whether a failure is imminent.

For binary classification specifically, Khelif et al.\ \cite{khelif2017direct} show
that a hand-crafted health indicator can match support vector machines on fixed-horizon
prediction.
Ramasso and Saxena \cite{ramasso2014application} make a point that shaped the
preprocessing decisions in this paper: raw C-MAPSS sensor readings carry substantial
engine-specific baseline offsets, so any meaningful comparison requires per-unit
normalisation before modelling.
Without it, differences between engines swamp the degradation signal.

What I could not find in the literature is a direct, cleanly-controlled comparison
between a single domain-informed feature and a full-sensor ensemble, evaluated
specifically on at-risk recall rather than RMSE, accuracy, or overall F1.
Papers that use simpler features tend to compare against other simple features.
Papers that use ensemble methods tend to optimise aggregate metrics.
The narrow question---does one number derived from expert knowledge of degradation
beat 21 raw channels on the metric that deployment actually requires?---does not seem
to have been asked this directly.
That gap is what this paper fills.

\section{Dataset}
\label{sec:data}

\paragraph{NASA C-MAPSS FD001.}
The Commercial Modular Aero-Propulsion System Simulation (C-MAPSS)
dataset~\cite{saxena2008damage} provides run-to-failure telemetry for turbofan engines
simulated under a single operating condition (FD001 subset).
Each row records one operational cycle for one engine unit: three operating-setting
columns and 21 sensor readings.
The training file contains 20,631 rows across 100 engine units, with per-unit cycle
counts ranging from 128 to 362 (mean 206).
No holdout test file is used; evaluation is performed on a held-out partition of
training engines.

\paragraph{Binary label definition.}
For engine $u$, let $C_u^{\max}$ denote its maximum recorded cycle (the failure point).
The Remaining Useful Life at cycle $c$ is $\mathrm{RUL}(u,c)=C_u^{\max}-c$.
We define:
\begin{equation}
  y_{u,c}=
  \begin{cases}
    1 & \text{if }\mathrm{RUL}(u,c)\leq 30 \quad\text{(at risk)}\\
    0 & \text{otherwise}\quad\text{(healthy)}
  \end{cases}
\end{equation}
This yields 17,531 healthy and 3,100 at-risk observations (14.4\% minority class).

\section{Methodology}
\label{sec:method}

\subsection{Sensor Preprocessing}

Several C-MAPSS sensors are constant or near-constant across FD001 and provide no
discriminative signal \cite{ramasso2014application}.
We retain 14 sensors with meaningful variance:
$\{s_{02},s_{03},s_{04},s_{07},s_{08},s_{09},s_{11},s_{12},s_{13},s_{14},s_{15},s_{17},s_{20},s_{21}\}$,
categorised by degradation direction:
rising sensors $\mathcal{R}=\{s_{02},\ldots,s_{15}\}$ (values increase with degradation)
and falling sensors $\mathcal{F}=\{s_{17},s_{20},s_{21}\}$ (values decrease).

Per-unit min-max normalisation removes engine-specific baseline offsets:
\begin{equation}
  \tilde{x}_{u,c,s}=
  \frac{x_{u,c,s}-\min_c x_{u,c,s}}
       {\max_c x_{u,c,s}-\min_c x_{u,c,s}+\varepsilon}
\end{equation}
where $\varepsilon=10^{-9}$ prevents division by zero.

\subsection{Degradation Score and Health-Window Feature}

We define a composite degradation score for each cycle:
\begin{equation}
  d_{u,c}=
  \frac{
    \tfrac{1}{|\mathcal{R}|}\!\sum_{s\in\mathcal{R}}\tilde{x}_{u,c,s}
    +\!\left(1-\tfrac{1}{|\mathcal{F}|}\!\sum_{s\in\mathcal{F}}\tilde{x}_{u,c,s}\right)
  }{2}
\end{equation}

A cycle is labelled \emph{degraded} if its score exceeds the 70th percentile of that
engine's score distribution:
\begin{equation}
  g_{u,c}=\mathbf{1}\!\left[d_{u,c}\geq Q_{0.70}(\{d_{u,c'}\}_{c'})\right]
\end{equation}

The \textbf{health-window feature} is the count of degraded cycles in the 10-cycle
rolling window ending at cycle $c$:
\begin{equation}
  h_{u,c}=\sum_{k=\max(1,\,c-9)}^{c}g_{u,k}
\end{equation}
This scalar encodes the recent degradation trajectory as a single interpretable value.

\subsection{Model A: Logistic Regression}

We train $\ell_2$-regularised logistic regression on the scalar $h_{u,c}$ with
class weights inversely proportional to class frequency (\texttt{balanced}).
This 1-feature model has a trivially interpretable decision rule.

\subsection{Model B: Random Forest Baseline}

A 100-tree Random Forest is trained on all 21 standardised raw sensor columns
(\texttt{class\_weight=`balanced'}, seed 42).

\subsection{Evaluation Protocol}

\paragraph{Unit-level split.}
80 engine units are used for training and 20 for testing (seed 42 shuffle).
All cycles from a given engine appear in exactly one partition, eliminating
temporal leakage from cycle-level random splits.

\paragraph{Primary metric.}
Recall on the at-risk class: the fraction of at-risk cycles correctly detected.
Weighted F1 is reported as a secondary reference.

\section{Discussion}
\label{sec:discussion}

The number I keep coming back to is 74.
Among the 620 at-risk test cycles, the Random Forest misses 74 of them---it predicts
\emph{healthy} for engines that are within 30 cycles of failure.
The logistic regression misses 12.
Both models were trained on the same data, evaluated on the same engines, with the
same class weighting.
The difference is that one model has a single feature that explicitly tracks how
recently each engine has been operating in a degraded state, and the other has 21
raw channels and enough capacity to find whatever patterns it wants.
On overall weighted F1, the Random Forest looks better.
On the question of how many imminent failures go undetected, it is considerably worse.

The interpretability point is worth making separately, not just as a bullet item.
The health-window feature $h_{u,c}$ takes integer values from 0 to 10.
The entire decision rule is: if $h_{u,c}$ is above some threshold, flag the engine.
You can explain that to a maintenance technician in two sentences.
The Random Forest's decision process, by contrast, involves 100 trees and 21 input
dimensions---it is not interpretable to anyone who does not already understand the
model.
That matters in industrial settings where the operator needs to understand why a
machine has been flagged before they will act on the alert.
There is also a practical edge-deployment argument: a single integer and a threshold
can run on microcontroller-class hardware; 21 standardised inputs through 100 trees
cannot.

The precision trade-off was larger than I expected.
At-risk precision for the logistic regression is 0.64, versus 0.83 for the Random
Forest---a 19-point gap.
When I look at the false positives, most occur in the cycles immediately before
$h_{u,c}$ crosses the decision boundary: the feature has accumulated some degraded
cycles but not enough for the engine to actually be in the last-30-cycle window.
The 10-cycle window length is a design choice, and a shorter window would likely
sharpen precision at some cost to recall.
I chose 10 because it is a round number that felt like a reasonable memory horizon
for a rolling health indicator; there is nothing principled about it, and tuning it
is the most obvious next step.

There are real limits to what this paper can claim.
The 70th-percentile threshold for labelling a cycle as degraded is a choice I made
without much justification beyond it feeling like a reasonable split between normal
operating variance and genuine degradation signal.
A learnt threshold---from an unsupervised anomaly detector, for example---would be
more defensible.
More importantly, FD001 is the simplest C-MAPSS subset: one operating condition, one
fault mode, 100 engines with relatively clean degradation trajectories.
FD002 through FD004 introduce multiple operating conditions and fault modes that would
likely break the assumption that a composite of rising and falling sensors cleanly
tracks health across all units.
I intend to test this.

\section{Conclusion}
\label{sec:conclusion}

A single rolling degraded-state counter gives a logistic regression 0.98 recall on
at-risk engine cycles in NASA C-MAPSS FD001.
A Random Forest on all 21 sensor channels gets 0.88.
The Random Forest has higher weighted F1.

I think the right way to read this result is not ``domain features always win'' but
``evaluation metric choice is a design decision with operational consequences.''
If you deploy a model that maximises weighted F1 on a 14\% minority-class dataset,
you are likely deploying a model that performs well on paper and misses failures in
practice.
The choice of what to optimise should come from the cost structure of the problem,
not from which number looks best in a table.
